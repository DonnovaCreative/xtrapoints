# Deploys & search-engine indexing

## Environments

| Environment | Domain | Builds from | `VERCEL_ENV` |
| --- | --- | --- | --- |
| Production | `xtrapoint.com` → `www.xtrapoint.com` | `main` branch | `production` |
| Staging | `staging.xtrapoint.com` | `staging` branch | `preview` (or a custom env name) |
| Preview | `*.vercel.app` | any branch / PR | `preview` |

The site is `output: 'static'` (Astro + `@astrojs/vercel`). Every deploy is a
**separate build**, so build-time signals like `VERCEL_ENV` are the reliable way
to differentiate environments.

## Getting new pages/routes onto production

Because production builds from **`main`**, any route only present on another
branch will **404 on production** even though it works on staging. Routes are
generated by `getStaticPaths()` at build time — if the source isn't in the
`main` build, the route doesn't exist.

➡ To ship staging work to production: **merge `staging` → `main`** and let Vercel
auto-deploy. (This is what fixed `/schools/*` 404ing on `www.xtrapoint.com`.)

## Indexing control (staging/preview de-indexed, production indexable)

Three layers, all designed so **production is never accidentally de-indexed**:

1. **`robots.txt`** — generated by [`src/pages/robots.txt.ts`](../src/pages/robots.txt.ts).
   Non-production builds emit `Disallow: /`; production emits `Allow: /` + the
   sitemap.
2. **`<meta name="robots" content="noindex, nofollow">`** — added in
   [`src/layouts/Layout.astro`](../src/layouts/Layout.astro) on non-production
   builds only.
3. **`X-Robots-Tag: noindex, nofollow` header** — [`vercel.json`](../vercel.json),
   applied by **hostname** (`staging.xtrapoint.com` and `*.vercel.app`).
   Production hosts are absent from every match, so they can never receive it.
   (A static build's `vercel.json` is shared across environments, so the header
   must key on hostname rather than `VERCEL_ENV`.)

The env decision for (1) and (2) is centralized in
[`src/config/site-env.ts`](../src/config/site-env.ts):

```ts
export const shouldNoindex = Boolean(vercelEnv) && vercelEnv !== "production";
```

This is an **allowlist of the one value that must stay indexable** (`"production"`).
An empty or unexpected `VERCEL_ENV` therefore can never noindex production.

Extra existing safeguard: `Layout.astro` sets `<link rel="canonical">` to the
**production** domain, so even an indexed staging page points search engines at
production.

> ⚠️ Depends on Vercel's **"Automatically expose System Environment Variables"**
> being enabled (default on) so `VERCEL_ENV` is present at build. If it were
> disabled, non-production builds would fall back to *indexable* — see the
> stronger follow-up below.

## Stronger follow-up: Deployment Protection

The robust fix for public staging access is **Vercel Deployment Protection**
(password or SSO) scoped to the staging/preview environments — a dashboard
setting (Project → Settings → Deployment Protection). That blocks all public
access (not just crawlers) and doesn't depend on build-time env detection.
Recommended in addition to the above.

## Verify

```sh
# Production school pages render (expect 200):
curl -sI https://www.xtrapoint.com/schools/sam-houston | head -n1

# Production stays indexable (expect Allow: /, and NO x-robots-tag):
curl -s  https://www.xtrapoint.com/robots.txt
curl -sI https://www.xtrapoint.com/schools/sam-houston | grep -i x-robots-tag   # (no output)

# Staging is de-indexed (expect Disallow: /, a noindex header, and the meta tag):
curl -s  https://staging.xtrapoint.com/robots.txt
curl -sI https://staging.xtrapoint.com/ | grep -i x-robots-tag
curl -s  https://staging.xtrapoint.com/ | grep -i '<meta name="robots"'
```
